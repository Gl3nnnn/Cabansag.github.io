Cloud computing felt overwhelming at first, but after certifying in Digital Transformation with Google Cloud, I decided to go deeper with AWS. This is the roadmap I am working from and the concepts that are starting to make sense.

To be clear about where this stands: I have not launched anything in AWS yet. There is no instance, no bucket and no credential behind this post. It is the plan, not a report, and I am writing it down now so that when I do have results they are written against something.

1. Start With the Big Three Services

Don't try to learn all 200+ AWS services. The foundation tier is really three things:

  • EC2 — virtual servers. Learn to launch, connect via SSH, and run a simple web server.
  • S3 — object storage. Upload files, set bucket policies, and understand availability.
  • IAM — identity and access. Learn users, roles, and the principle of least privilege.

2. Spin Up a Free-Tier EC2 Instance

Launching something and deleting it is the part of this I most want to do, and the part I have not done yet. The steps, as I understand them, are short enough to be the first thing that goes from reading to doing:

# the sequence I plan to run on a free-tier instance
sudo apt update
sudo apt install -y nginx
echo "<h1>Hello from EC2</h1>" | sudo tee /var/www/html/index.html

The value is not the page. It is finding out what the console actually feels like, which is exactly the part documentation is worst at.

3. Manage Firewalls With Security Groups

The default security group blocks most traffic, so an instance that boots with nothing open is unreachable by design. Opening port 22 for SSH and port 80 for HTTP is the minimum needed to use it at all, and it is also where the security lesson lives: a misconfigured group can expose an instance to the whole internet, and default rules are about convenience rather than safety.

Least privilege is not optional, and understanding why is a better reason to learn IAM than memorising the policy grammar.

4. Docker Changed How I Think About Deployment

This is the one place I can speak from experience, because I containerized this portfolio and can confirm it runs the same way on my machine every time. A simple Dockerfile plus an image pull is what would let the same app run on EC2 without setup drama, though I have not done that second part yet:

docker build -t my-app .
docker run -d -p 8080:80 my-app

5. Keep the Bill at Zero

The thing that puts people off cloud is the bill. The rule I am setting for myself now, before I start: use the free tier, tag everything, and terminate what I am not using. The habit to check billing after every session is the one I am most likely to skip on the first attempt, so it is the one I am writing down.

Cloud skills are about making systems scalable and reliable — but wisdom is knowing when to shut things down.

What's Next

CI/CD is what I am aiming at after that — a small project on GitHub with an automated workflow testing and deploying it to EC2. The path from developer to cloud-ready is a series of small, repeated experiments, and I am on experiment zero.
