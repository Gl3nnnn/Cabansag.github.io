Dockerizing My Portfolio: Containers Made Simple

2026 Glenn Patrick Cabansag 7 min read

My portfolio is a plain static site — HTML, CSS, and a bit of JavaScript. It's simple enough to open with a double-click, so why bother with Docker at all? Because learning to ship even a tiny project in a container teaches you how deployment behaves on a real server. Here's how I containerized this very site.

1. Images vs. Containers

The mental model that finally made Docker click: an image is a frozen recipe — a snapshot of the OS, runtime, and files. A container is a running instance of that recipe. You can run five containers from one image, like running five copies of the same app in isolated boxes.

2. Writing the Dockerfile

For a static site, the classic approach is a small web server. I used nginx:alpine because it's tiny and purpose-built for serving files. The Dockerfile is just three lines:

FROM nginx:alpine
COPY . /usr/share/nginx/html
EXPOSE 80
  • FROM picks the base image — here, a minimal nginx with Alpine Linux
  • COPY drops my site files into the folder nginx serves by default
  • EXPOSE documents that the container listens on port 80

3. Build and Run

Two commands turn the Dockerfile into a working site:

docker build -t portfolio .
docker run -d -p 8080:80 --name portfolio portfolio

Now http://localhost:8080 serves the exact same files that GitHub Pages serves. The -p 8080:80 maps my host port to the container's port 80, so any port on the host can point at the container's port.

4. Live Reload with Volume Mounts

Rebuilding the image after every edit gets old fast. A bind mount overrides a folder in the container with a folder on my machine, so changes appear instantly:

docker run -d -p 8080:80 -v "%cd%":/usr/share/nginx/html --name portfolio portfolio

Now I edit index.html locally, refresh the browser, and the container already serves the new file. No restart needed.

5. One Command with Docker Compose

As soon as an app grows past one container, typing docker run for each one becomes error-prone. docker-compose.yml turns everything into a single command:

services:
  portfolio:
    build: .
    ports:
      - "8080:80"
    volumes:
      - .:/usr/share/nginx/html
docker compose up -d

6. Why This Matters

If it runs the same way on my laptop as it does on a server, half of the mysteries of deployment disappear.

Containerizing this site gave me the vocabulary and confidence to approach bigger things — the Laravel and PHP apps I work with at my job, and eventually pushing images for real cloud deployments. The skill transfers; the static site is just the cheapest possible scaffold to practice on.
